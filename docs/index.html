simcheck

Hand off iOS testing to a pool of pre-booted simulators. An agent submits a build, a test scenario and the screenshots it wants back — and gets evidence, not assurances.

What it is

An agent that has just changed iOS UI code has no way to know it worked. It can read the diff, it can reason about the view hierarchy, and it can still be wrong. simcheck closes that loop: it runs the build on a real simulator, drives the flow, and returns named screenshots.

The output is designed to be pasted into a pull request. A reviewer sees the verdict, the assertion it was judged against, and a picture of the screen — rather than a claim that the toggle now works.

The rule it enforces: a run only passes if every screenshot you asked for actually exists. If the flow never reached that state, the run fails — which is a real signal, not a harness bug.

Features

Warm simulator pool

N simulators kept booted and idle. No cold-boot tax on the first run, and pool size is the concurrency limit.

Natural language or exact steps

Describe the flow in English, or give precise taps. Either way you get a replayable step list back.

Screenshots as evidence

Named captures returned as images an agent can actually look at, plus a markdown report for the PR.

Submit and poll

Runs return a job id immediately and queue as pending. Long-poll for completion; nothing blocks.

Scoped tokens

Capability-based auth. A remote token can never name a path on your machine — it runs uploaded builds only.

Clean between runs

Each device is reset and its screen sanitised, so one run's permission dialog can't break the next.

How it works

A daemon owns a pool of simulators and a queue of runs. Everything else — the CLI, the MCP server, your agent — is a client of its HTTP API.

A run moves through these states:

StateMeaning
pendingQueued. No simulator free yet.
preparingDevice leased; building or installing.
runningDriving the app.
passedAssertion held and every requested screenshot exists.
failedIt ran, but the assertion didn't hold or a screenshot was unreachable.
errorThe harness or the build broke. Not a verdict on the app.
timeout / cancelledRan out of time, or was stopped.

The pool

Simulators are kept booted so a run starts immediately. A device added to the pool is pending until it has been booted, then ready; it becomes leased for the duration of a run and recycling while it is reset.

It only touches its own devices. The pool creates, boots, erases and deletes simulators named simcheck-* and nothing else. The simulators you use in Xcode are never affected.

Recycling uninstalls the app and then sanitises the screen. That second step matters more than it sounds: uninstalling an app does not dismiss a system alert it left behind — an "Allow X to access your calendar?" sheet belongs to SpringBoard and would silently swallow the next run's taps. So the device is returned to the home screen, any leftover modal is dismissed (always choosing the declining option, never granting a permission), and the device is rebooted if that fails.

Two ways to describe a test

Natural language — an agent reads the accessibility tree, works out the taps, and captures the screenshots you named: 

{
  "app": { "project": "App.xcodeproj", "scheme": "App" },
  "scenario": "Sign in as demo@example.com / hunter2, open Settings, turn on Beta Features.",
  "screenshots": ["signed-in", "beta-on"],
  "assert": "The Beta Features toggle reads On."
}

Explicit steps — deterministic, no model in the loop, no token cost:

{
  "app": { "path": "/abs/path/App.app" },
  "screenshots": ["beta-on"],
  "steps": [
    { "action": "tap", "id": "beta_toggle" },
    { "action": "screenshot", "name": "beta-on" }
  ]
}

Every natural-language run returns executedSteps — the exact actions it took. Lift those into a steps run and a one-off exploration becomes a repeatable regression check that costs nothing.

Install

Requires macOS, Node 20+, Xcode with an iOS simulator runtime, and Homebrew.

git clone <repo> ~/Developer/simcheck
cd ~/Developer/simcheck
./install.sh

That checks your toolchain, installs the AXe simulator driver, builds, links simcheck into ~/.local/bin, registers a launchd agent so the pool is warm after a reboot, and installs the Claude skill and MCP server.

Then confirm the environment is sane:

simcheck doctor

Most common failure: your Xcode SDK is older than your installed simulator runtimes. xcodebuild cannot target a runtime newer than its SDK, so every build-from-source run fails with a confusing "no destination" error. doctor detects this and tells you which to change.

Connect an agent

simcheck speaks MCP over stdio, so any MCP-capable agent can drive it. To get the exact config for your machine, with real paths already filled in: 

simcheck mcp-config          # all of them
simcheck mcp-config codex    # just one

One command, applied to every session:

claude mcp add simcheck --scope user -- /opt/homebrew/bin/node ~/Developer/simcheck/dist/mcp.js

Verify with claude mcp list. The installer also drops an ios-sim-test skill into ~/.claude/skills/, which teaches Claude when to reach for the harness and how to write a good scenario.

Edit ~/Library/Application Support/Claude/claude_desktop_config.json:

{
  "mcpServers": {
    "simcheck": {
      "command": "/opt/homebrew/bin/node",
      "args": ["/Users/you/Developer/simcheck/dist/mcp.js"]
    }
  }
}

Quit and reopen Claude Desktop. Paths must be absolute — ~ is not expanded.

Add to ~/.codex/config.toml:

[mcp_servers.simcheck]
command = "/opt/homebrew/bin/node"
args = ["/Users/you/Developer/simcheck/dist/mcp.js"]

Or let the CLI do it:

codex mcp add simcheck -- /opt/homebrew/bin/node ~/Developer/simcheck/dist/mcp.js

~/.cursor/mcp.json for every project, or .cursor/mcp.json for one:

{
  "mcpServers": {
    "simcheck": {
      "command": "/opt/homebrew/bin/node",
      "args": ["/Users/you/Developer/simcheck/dist/mcp.js"]
    }
  }
}

.vscode/mcp.json in the workspace:

{
  "servers": {
    "simcheck": {
      "command": "/opt/homebrew/bin/node",
      "args": ["/Users/you/Developer/simcheck/dist/mcp.js"]
    }
  }
}

VS Code's top-level key is servers, not mcpServers as everywhere else. Copying another client's config verbatim will silently fail.

It is an ordinary stdio MCP server, so any compliant client works — Windsurf, Zed, Gemini CLI, opencode, your own. Point it at: 

command: /opt/homebrew/bin/node
args:    ["/Users/you/Developer/simcheck/dist/mcp.js"]

Most clients use the same JSON shape as Claude Desktop. If yours has no MCP support at all, drive the HTTP API directly — see Reference — or shell out to the simcheck CLI, which is equally scriptable.

First run

No build needed — this drives the simulator's own Settings app:

simcheck submit examples/settings-steps.json --wait

Or ask your agent, in plain English:

Run the login flow on a simulator and show me a screenshot of the
settings screen with dark mode on.

Everything a run produces lands in ~/.simcheck/runs/<id>/:

report.md          the evidence write-up
screenshots/*.png  every named capture, plus final-state
run.json           full state, including executedSteps and the trace
app.log            the app's own log output
build.log          xcodebuild output, when built from source

Security

Read this before exposing it. Submitting {"project": "App.xcodeproj"} makes the daemon run xcodebuild, and Xcode Run Script build phases execute arbitrary shell as you. Anyone who can name a local project has code execution on that Mac. That is inherent to any build service — which is why tokens are scoped rather than all-powerful.

By default the daemon binds 127.0.0.1 only, and refuses to bind any wider address while edge authentication is off.

Scoped tokens

Secrets are stored as SHA-256 hashes; the plaintext is shown once, at creation.

PresetCan name local pathsFor
fullyesAgents on this machine
remotenoAnything off-machine — uploads a built .app instead
readonlynoPolling and reading results only
simcheck whoami                              # what this token may do
simcheck token create cloud --preset remote  # secret printed once
simcheck token revoke cloud

Every submission, upload and refusal is appended to ~/.simcheck/audit.log, tagged with the token that did it.

Reaching it from elsewhere

Don't publish it directly. Put an authenticating proxy in front, so unauthenticated traffic never reaches the Mac.

ModeUse for
cloudflare-accessA client that can't run a VPN — a cloud agent sandbox. The daemon verifies the Cf-Access-Jwt-Assertion JWT itself.
trusted-proxyA ZTNA broker or internal reverse proxy — a Netskope Private Access publisher, an internal load balancer.
simcheck tunnel sim.example.com

That scaffolds a Cloudflare Tunnel and prints the remaining steps — and deliberately creates nothing in your Cloudflare account.

Why verify in the origin? If you only trust "it arrived through the tunnel", anyone who reaches the origin by another route walks straight past Access. The daemon checks the signature, issuer, audience and expiry on every request.

On a network that inspects TLS — Netskope, Zscaler and friends — set caBundle to the corporate root CA and re-run ./install.sh. Node reads NODE_EXTRA_CA_CERTS once at startup, so it has to be in the launchd plist; doctor warns when the two disagree.

Where to run it

On your own machine default

Agent and pool on the same Mac, talking over loopback. Source never leaves the box and builds stay incremental. If your repos are IP-protected, this is the shape you want — there is no new egress to sanction.

Build here, test there

simcheck upload --scheme App --project App.xcodeproj builds, zips and uploads; the far side references the artifact id. Only the compiled bundle moves, never the source.

A shared team pool

Uploading per run gets wasteful. The efficient shape is the shared Mac fetching a git ref itself, with clients passing only a sha.

HTTP API

Bearer token on every route except /health; each checks a capability.

POST   /v1/runs                          submit; 202 with the run id
GET    /v1/runs/:id                      full state
GET    /v1/runs/:id/wait?timeoutMs=      long-poll until terminal
GET    /v1/runs/:id/report               markdown
GET    /v1/runs/:id/screenshots/:name    PNG
DELETE /v1/runs/:id                      cancel
POST   /v1/artifacts                     upload a zipped .app
GET    /v1/pool                          pool state
GET    /v1/whoami                        this token's capabilities
GET    /health                           liveness

Actions available to a step or scenario

tap (by id, label, value or x/y), type, clear_text, press_enter, swipe, gesture, button, wait, wait_for, screenshot, open_url, appearance, permission, launch, relaunch, terminate, describe_ui.

Prefer id over label over coordinates. SwiftUI needs an explicit .accessibilityIdentifier(...) for id targeting to work — worth adding as you go, since it makes every future test cheaper.
